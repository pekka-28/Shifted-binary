Using shifted binary in XSLT – Foundry

Financial services trading systems exchange structured messages to submit orders to brokers and trading venues. Simple Binary Encoding (SBE) provides a compact binary message format; FIX Markup Language (FIXML) expresses the business information as XML, using the conventions of the FIXML Technical Standard v1.1 [4]. This case study follows an order-submission message, called New Order Single, from its binary representation through shiftedBinary XML to FIXML.

The guide is for developers using XSLT 1.0 [2] to select binary message layouts, extract their fields and construct XML output. It explains the complete example: an instruction to buy 7 units of GEM4 at a limit price of 99.610. Shifted binary reader guide – Foundry [1] explains the representation and its alternatives. Here, the focus is the transformation: each input byte becomes one XML-safe character that XPath can compare and slice directly.

The order on the wire

The order contains a client identifier, account, instrument, side, transaction time, quantity, order type, price and an optional stop price. The SBE schema [3] defines their binary layout. The framed message contains 68 bytes: a 6-byte Simple Open Framing Header (SOFH), an 8-byte SBE header and a 54-byte fixed-length body. SOFH integers use big-endian byte order; SBE integers use little-endian byte order.

This example adapts the standard's order to use schema identifier 100 consistently with its schema; the published wire example uses 91. The timestamp below follows the encoded bytes, which differ from the standard's explanatory timestamp. This is an adapted case study, not an unchanged reproduction of the standard's wire example. Offsets in the following display are hexadecimal and are not part of the message.

Fragment Framed SBE order bytes

0000    00 00 00 44 EB 50 36 00 63 00 64 00 00 00 4F 52
0010    44 30 30 30 30 31 41 43 43 54 30 31 00 00 47 45
0020    4D 34 00 00 00 00 31 00 84 68 90 FE A8 9A 13 07
0030    00 00 00 32 1A 85 01 00 00 00 00 00 00 00 00 00
0040    00 00 00 80

Carry the bytes in XML

A binary-to-XML converter reads the binary message and writes an XML message whose binary element contains canonical shifted characters. Each byte b becomes U+E100 + b. For this order, string-length(binary) is therefore 68, regardless of whether the XML file uses UTF-8 or UTF-16. The shifted payload occupies 204 bytes in UTF-8 or 136 bytes in UTF-16, excluding markup and any byte-order mark; those storage sizes are separate from the original 68-byte message length.

The following is the complete message, with no whitespace inserted inside binary. Its display font shows the original byte values in place. The hexadecimal listing above provides the same values when the font is unavailable. Save it as NewOrderSingle-shifted-message.xml; the archive also includes this input.

Fragment NewOrderSingle-shifted-message.xml

<!-- NewOrderSingle-shifted-message.xml -->
<message><binary></binary></message>

Canonical input makes character positions identical to byte positions apart from the indexing convention: wire offsets start at zero and XPath positions start at one. Keep this form throughout selection and slicing. The mapping tables accept some mixed representations, but this case study requires every payload character to lie in U+E100–U+E1FF. Do not insert line breaks into the payload or apply normalize-space() to it.

Select the message layout

The transformation recognises ten bytes starting at wire offset 4: the SOFH encoding and the complete SBE header. Their value is EB 50 36 00 63 00 64 00 00 00. XPath selects those ten characters with substring(binary, 5, 10) and compares them with the corresponding shifted literal. No numeric conversion is needed to choose the template.

Table Header signature

Wire offset Width Field Value
0 4 SOFH length, outside the signature 68
4 2 SOFH encoding EB50: little-endian SBE
6 2 SBE block length 54
8 2 Template identifier 99: New Order Single
10 2 Schema identifier 100
12 2 Schema version 0

The template's opening tag is shown below as an excerpt. The prefix gen in the archived stylesheet denotes the ordinary XSLT namespace, http://www.w3.org/1999/XSL/Transform; it does not introduce an extension language. The literal is ten shifted characters, not twenty hexadecimal digits.

Fragment Message-selection template opening

<gen:template priority="2"
  match="message[substring(binary, 5, 10) = '']">

The framing length is outside the signature because it describes the complete message. For this fixed-layout profile it must agree both with the available 68 characters and with the 6 + 8 + 54 bytes required by the layout. The signature identifies a specific schema version and block length; it does not implement general SBE version negotiation.

Rendering caution: The shiftedBinary constants may appear as empty boxes or unavailable glyphs when the display font is missing or the viewer does not select it. This affects their appearance, not the stored characters or the transformation. The header constant above can equivalently be written in XML source as &#xE1EB;&#xE150;&#xE136;&#xE100;&#xE163;&#xE100;&#xE164;&#xE100;&#xE100;&#xE100;. XML parsing turns these references into the same ten characters. The samples use the literal characters so that the byte pattern is directly visible when the font is available.

Extract and interpret the fields

Inside the selected template, $bytes is string(binary). The expression substring($bytes, 15, 8) selects the client order identifier at wire offset 14. Every field uses the same operation; its width comes from the schema. Table Order fields gives the XPath positions and the separate business interpretation needed to build FIXML.

Table Order fields

Field XPath start Width Interpretation FIXML destination
ClOrdID 15 8 ASCII ORD00001 Order/@ID
Account 23 8 ASCII ACCT01, NUL padded Order/@Acct
Symbol 31 8 ASCII GEM4, NUL padded Instrmt/@Sym
Side 39 1 ASCII 1: Buy Order/@Side
TransactTime 40 8 Unsigned epoch nanoseconds Order/@TxnTm
OrderQty 48 4 Signed mantissa 7, exponent 0 OrdQty/@Qty
OrdType 52 1 ASCII 2: Limit Order/@Typ
Price 53 8 Signed mantissa 99610, exponent −3 Order/@Px
StopPx 61 8 Signed 64-bit null sentinel Omitted

For ASCII fields, the mapping stylesheet translates shifted characters to their byte-valued characters. A fixed-width string ends at its first NUL padding byte. The account can be read using the following excerpt, evaluated with $bytes and the imported mapping variables in scope:

Fragment Account extraction

<xsl:variable name="accountBytes" select="substring($bytes, 23, 8)"/>
<xsl:variable name="accountText"
  select="translate($accountBytes, string($canonicalShifted), string($shiftedText))"/>
<xsl:value-of select="substring-before(concat($accountText, ''), '')"/>

The NUL remains shifted U+E100, written literally in the expression above; its escaped XML-source equivalent is &#xE100;. It can serve as the delimiter without introducing a forbidden XML character. Appending a NUL before taking substring-before() also handles an identifier that fills its entire field. The result here is ACCT01. The same operation yields ORD00001 and GEM4. Side and order type are ASCII codes: bytes 31 and 32 mean characters 1 and 2, not numeric byte values 1 and 2.

Numeric fields need byte-order and type interpretation after slicing. The reference templates recover a byte's numeric value from its position in the canonical mapping alphabet. For an unsigned little-endian value, they process the most significant byte first and repeatedly calculate result * 256 + byte. Quantity bytes 07 00 00 00 give 7. Price bytes 1A 85 01 00 00 00 00 00 give 99610; the schema's exponent −3 gives 99.610. The exponent is schema metadata, not an extra byte in this field.

The timestamp bytes 00 84 68 90 FE A8 9A 13 represent Unix epoch nanoseconds. Formatting the sample at millisecond precision gives 2014-10-06T20:27:24.432Z. Stop price bytes 00 00 00 00 00 00 00 80 are the signed 64-bit null sentinel. Compare that raw fragment before numeric conversion and omit the attribute when it matches; a missing optional price is different from a price of zero.

The null stop-price test is also an ordinary string comparison. In the following excerpt, equality with the literal eight-character sentinel means the optional field has no value; the template body emits the attribute only when the comparison is unequal.

Fragment Optional stop-price condition

<xsl:if test="substring($bytes, 61, 8) != ''">
  <!-- Emit the decoded StopPx attribute here. -->
</xsl:if>

The sentinel's escaped XML-source equivalent is &#xE100;&#xE100;&#xE100;&#xE100;&#xE100;&#xE100;&#xE100;&#xE180;. This comparison works on the original bytes without first turning the sentinel into a 64-bit number.

Slicing remains exact for all these fields because it operates on characters. Numeric interpretation has separate precision requirements. The supplied reference code uses XPath 1.0 numbers and is not an exact general-purpose 64-bit decoder; its limitations are recorded at the end of this guide.

Construct the FIXML order

The FIXML Technical Standard v1.1, §2 and §4.3 [4], describes the XML naming conventions and single-message structure used here. The target namespace identifies FIX 5.0 SP2. The stylesheet writes an Order with its identifiers, side, time, type and price, followed by Instrmt and OrdQty children in the FIXML namespace [4]. The SBE schema determines how to read the bytes; the explicit business mapping determines these XML names and locations. FIXML is a semantic projection, not a second wire encoding prescribed by the SBE schema. Header fields describe the binary transport and layout and do not become business attributes.

The complete result is shown below. The null stop price is absent. This profile has no TimeInForce field, so the transformation does not invent one. The XML serializer writes the markup and escapes any special characters in the resulting attribute values.

Fragment FIXML result

<!-- NewOrderSingle-result.fixml.xml -->
<FIXML xmlns="http://www.fixprotocol.org/FIXML-5-0-SP2"
       v="FIX.5.0SP2">
  <Order ID="ORD00001" Acct="ACCT01" Side="1"
         TxnTm="2014-10-06T20:27:24.432Z" Typ="2" Px="99.610">
    <Instrmt Sym="GEM4"/>
    <OrdQty Qty="7"/>
  </Order>
</FIXML>

This is the practical benefit of shifted binary in the transformation: ordinary XPath selects the layout and extracts byte fragments, while reusable templates interpret only the fields whose business values are needed. The font makes the literals readable; it plays no part in executing the stylesheet.

Reference implementation limits

The sample transformation produces the FIXML shown above, but the supplied decoder has two defects that matter beyond this demonstration. Its framing check does not enforce the complete body size: a truncated message with an adjusted framing length can be accepted. Its unsigned-then-signed 64-bit arithmetic can lose precision: a price mantissa of −1 produced 0.000 instead of −0.001. A production implementation must enforce the selected layout's length and use exact arithmetic for the integer ranges it supports.

Timestamp output rounds to milliseconds and assumes nonnegative Unix timestamps. The profile covers one flat fixed-length order, not repeating groups or variable-length fields; the generator fixes schema version zero. These limitations concern the supplied interpretation code, not the lossless one-character-per-byte representation.
